## 0. 一句话结论

**分数主要丢在两段：**

1. **候选召回（池外分子）**——主引擎每题的候选窗口只有 **107 个结构（中位数）**，PubChem 通道同样题目的窗口是 **≈9,400 个（中位数，12 点抽样 1,160–27,293）**，是主池的 ~85 倍；但 PubChem 每題只返回 25 个提案、只占 **5 个固定槽位**、只有 1 个升位名额（`S>6 且 pop≥5`，或 `rel>150`）。这是全管线最不对称的地方。
2. **同分子式异构体 rank-1（池内、无参考谱结构）**——池 710,701 个结构里只有 275,810 个（38.8%）在训练谱库里；其余 434,891 个（61.2%）只能靠指纹/类似物/碎片/预测谱排序。这一类的 top-1 目前没有独立证据源，全靠 LightGBM ranker + ICE/GL。

还有一个刚测出来的事实把第 1 点钉死了：外部留出集 **Enveda-180 的 3,719 个结构，0 个在 710k 池里，但抽样的 20/20 都在 PubChem**（§3.5）。**"池外"不等于"不可达"；PubChem 是唯一能把这类结构拉回来的桥，而它现在只被允许进 5 个槽。**

**最可能大幅提分的新信号：把 PubChem 通道做成"一等候选流"**（深度、公式先验、碎片复核、升位与槽位按证据分级），而不是继续在 25 名内部调权重。预期 +0.005～+0.02（区间来自第 4 节的分解），成本是 0 个新数据集、约 +40 分钟 CPU。【推断】

## 1. 执行栈：谁决定候选，谁只改顺序

068a 不是一条管线，而是 **"frozen 0.465 决定候选集合 + 068a 覆盖层只做重排"**。

```
[cells 5–13]  配置 + 物化源码（8 个 helper 模块 + FROZEN_B64）
      │
[cells 14–15] materialise_sources() / run_public_pipeline()
      │        └─ runner.py 逐格执行 frozen 0.465 notebook（独立进程）
      │           产出 submission_baseline0465.csv + frozen_candidate_evidence.parquet
      │
      ├─ neural_scores.py  ×2（public bundle / popwenman v80）+ 0.5/0.5 z 融合
      ├─ outsiders.py      收集 frozen 25 名之外的候选并打分（rescue 用）
      └─ consensus.build_variants() → variants/submission_{V0,V1,V2,V3,V4,CUSTOM}.csv
      │
[cells 15–16]  CUSTOM = w_top 0.25 / w_mid 0.75 / rescue 0  →  submission.csv
      │        parallax_physical.apply()  片段检查（只动 leader / 2–10 邻位 / 第 25 名）
[cells 20–21]  v8 质量表（MASS_PEN）+ Variant M 合并（doc prior + k14 去重 + 空槽回填）
[cells 23]     v8 质量 rank-1 规则（MASS_LEAD_OFF=5 ppm；RR8 学习重排 **关闭**）
[cells 24]     N-1c 测试集内分子网络重排（LAM=0.35, TAU=0.6）
[cells 25]     APEX 外谱库 rank-1 提升（TAU=0.80, K=4, LIB_TAU=0.90）
```

**关键结构事实（已核实）**：`choose_and_submit()`（cell 15，L214-239）选的就是 `variants/submission_CUSTOM.csv`，而 CUSTOM 是 **对 frozen 0.465 的 25 个候选做 RRF 重排**（`consensus.leader_safe_order`），`rescue=0`。后面的所有覆盖层（物理、Variant M、质量、N-1c、外谱）都只在 **这 25 个候选内部换序**，例外只有两处：

- Variant M §2b 的 `outsider_fills`：仅在 InChIKey14 去重把列表压到 25 以下时才补（cell 21，L226-239）；
- Variant M §2c 的 LOTUS 回填：同样只在空槽（L240-252）。

所以：**068a 的候选召回 = frozen 0.465 的候选召回**。任何"新信号"若不能进入 frozen 的 25 名，或不能挤掉其中一个，对分数就是零。

## 4. 分数损失在哪一段

### 4.1 已验证的三条硬约束

1. **候选集合被冻结在 0.465 的 25 名**（`rescue=0`，`leader_safe_order` 只换序）。068a 所有新层（物理/Variant M/质量/N-1c/外谱）都不能新增候选，除非去重产生空槽。
2. **N-1c 只改 2/400 条列表**，且 top-1 一条都没改；`LAM` 0.25→0.35 的 +0.004 就是这 2 条 mid-rank 的边际。
3. **外谱 overlay 0 命中**；LOTUS、DreaMS 未挂载。也就是说：**"新数据源"这一层目前全部是零**，0.492 完全由 frozen 0.465 + 神经重排 + 5 个调参层构成。

### 4.2 MRR 分解（推断）

公开消融给出的上界很硬：alexchilton 的 59 臂里只有 4 个旋钮 > +0.002，最大 +0.006；33 个退步。这说明 **在现有候选集合内，排序已经接近饱和**。那么 0.492 的构成只能是：

| 名次段 | 占比（假设） | 对 MRR 贡献 |
| --- | --- | --- |
| rank 1 | 0.43 | 0.430 |
| rank 2 | 0.06 | 0.030 |
| rank 3 | 0.03 | 0.010 |
| rank 4–10 | 0.02/名 | 0.019 |
| rank 11–25 | 0.004/名 | 0.002 |
| **合计** | recall@25 ≈ **0.72** | **≈0.491** |

**推断结论：约 28% 的分子在 25 名内完全没有正确答案**。这 28% 里，主池只覆盖"一个分子式的 ~107 个异构体"，因此只要真结构不在池里（或不在那个公式里），得分必然是 0。**召回是主损失项，不是排序。**

对照证据：sanpier 的 120 分子 NP 面板（答案都在池内）`main_only` test MRR **0.942**、top1 0.933、recall@25 0.967；同一套代码在公榜只有 0.49。**池内 0.94 / 公榜 0.49 的落差，就是"池外 + 无参考谱"这两类的代价。**

### 4.3 池内结构的证据缺口（已核实）

- 池 710,701 − 谱库 275,810 = **434,891 个结构（61.2%）没有任何参考谱**。
- 这些结构只能靠：FPNet 指纹、analog propagation、MetFrag-lite 碎片、ICEBERG/GLACIER 预测谱、PubChem 文档先验。
- 竞赛方说明隐藏集包含"有公开参考谱 / 库内无参考谱 / 库外 de novo"三类，比例未公开（`docs/remote-workflow.md`）。第二类正好落在上面这 61.2% 里。

**所以损失排序是：**

1. **池外（≈28% 的零分分子中大部分）**——唯一宽通道是 PubChem，而它被 5000→25→5 卡死；
2. **池内无参考谱（61.2% 的池）**——没有独立的谱学证据源，rank-1 靠 ranker；
3. **同分子式异构体 mid-rank**——已被 5 层调参榨干（N-1c、libcos、own-hn 三次 +0.000～+0.001）。

### L3（第三）库 k-NN 结构投票 + "答案是否在池内"的置信度

**为什么是它**：现有库匹配是"每个结构一个合并分"（`lib_max`），没有"多个邻居谱投票"，也没有"最大余弦低 → 答案可能不在池内"的显式判据。后者可以直接驱动 L1 的升位。

**改哪里**

- 新增一个模块（照 `outsiders.py` 的形状），读 2.5M 谱索引，对每个 query 取 top-k 邻居（modified cosine，sqrt 强度，0.01 Da 分箱），对邻居结构投票：`vote(s) = Σ_n cos_n^p · 1[structure(n)=s]`。
- 用在两处：
  1. cell 21 的 2–25 名：小权重 `w_knn`（建议 ≤0.15）加到 `_score_cand`；
  2. cell 43 的升位门控：`max_cos < 0.5`（无邻居）时允许 PC leader 升位；`max_cos ≥ 0.85` 时保护池内 leader。
- **不要**动 rank 1 的池内顺序（`066a` 的连续余弦 mid-rank 已经证明是中性）。

**输入数据**：`train.parquet`（2.5M 谱）。索引构建参考 066a：**182,941 结构 / 2,539,608 行**，约 30 分钟。【已核实·运行】两处口径不同：`train.parquet` 有 275,810 个 unique `inchikey14`，066a 的 mid-rank 索引只剩 182,941 个结构，说明索引侧还有一层结构过滤（具体条件需读 066a 的建索引代码确认）；做 L3 前必须先统一这个口径。【推断】

**离线验证（这是任务 4(b) 的核心）**：按 `inchikey14` 整组留出 2,000 个结构，删掉它们的全部谱，构造 query；对每个 query 用剩余谱做 k-NN，测：

- `recall@25`：top-25 投票结构里是否含真值；
- `MRR@25` / top-1：与"现有库匹配 + ranker"在同一候选集合上的对照；
- 分两层看：`max_cos≥0.8`（有近邻）与 `<0.5`（无近邻）。

**预算**：索引 30 分钟 CPU + 查询 400 題秒级；**不需要 GPU**。

**风险**

- 高：与现有库匹配高度共线（同一批谱），增量主要是"多邻居聚合"与"置信度"，可能重演 066a 的中性。
- 中：留出集的 `max_cos` 分布与隐藏集不同（隐藏集有"库内无参考谱"类），离线 recall 会高估。

**预期**：`+0.000～+0.01`；主要价值在**给 L1 提供升位门控**，而不是单独提分。

## 6. 两个具体假设的评估

### (a) 把 LOTUS / COCONUT / NPAtlas 按 neutral mass 扩展进**主候选列表**（而不是第 25 名空槽）

**现有代码是否已等价实现？**

- **COCONUT：完全等价，已实现。** Engine 1/2 的 710,701 池里 COCONUT 占 **436,389**（`coco_mass.npy` 字节数 ÷ 8），且窗口规则就是 ±10 ppm。再把 COCONUT 按质量加一遍是**纯重复**。【已核实】
- **LOTUS：没有实现。** 只有 `pc_lotus_refs`（作为 PubChem 候选的文献先验，`LOTUS_W=0.5`）和 cell 21 §2c 的空槽回填；`candidates_lotus.parquet` 未挂载。【已核实】
- **NPAtlas：没有实现**，也没有任何挂载的数据集。【已核实】
- **DreaMS NP：只填空槽**，且数据未挂载。【已核实】

**增量在哪？**

1. LOTUS 与 COCONUT 高度重叠（LOTUS 是 COCONUT 的主要来源之一），**净新增结构预计只有几万量级**，需要先用两个结构的 `inchikey14` 求差集实测（本地可做，30 分钟）。
2. 真正的增量不是"结构数"，而是**这 434,891 个无参考谱结构如何在 25 名里排序**。把它们塞进列表而不给证据，只会挤掉正确答案。
3. 因此 (a) 的正确形态是：**"质量窗口 + 证据评分 + 配额"**，而不是"回填空槽"。具体：给 NP 候选算 `0.4·analog_Tanimoto(top5) + 0.3·doc_prior + 0.2·NP_membership + 0.1·neural`，只在 `lib_max<0.6` 的題里占 **2–3 个中段槽位（8–15 名）**。

**如何离线测 recall@25**

- 用 `casmi26-natural-product-panel-benchmark` 的 120 分子面板（有标签，`panel_audit.json`：60 train/30 test/30 calibration）。【已核实】
- 指标：`gold_in_final25`（现状 29/30）、`MRR@25`（现状 0.942）。加入 NP 扩展后看是否 ≥ 现状；**注意这个面板的答案都在池内，无法验证"池外 NP"**，所以还要用 (b) 的整组留出集做第二组。
- 只有当"扩展后仍保留全部 gold + 新候选带来 rank 提升"时才算正收益；否则会重演 tail rescue 的 −0.006。

**结论**：**(a) 作为"候选召回"手段价值很低（COCONUT 已在池内，LOTUS/NPAtlas 增量小且无谱证据）；作为"给无谱结构排序"的手段才有价值，但那本质上是 L2，不是"扩展列表"。** 【推断，基于已核实的池组成】§3.5 的 e180 实测进一步说明：连 COCONUT 都不含 Enveda 自己的 3,719 个结构，再往里加 LOTUS/NPAtlas 也救不了这一类；能覆盖它们的是 PubChem（20/20），所以资源应该花在 L1 的通道深度上，而不是把 NP 结构塞进 25 名。

### (b) 用 275k train structures 的谱做 k-NN 检索，给每个 query 直接投结构票

**现有代码是否已等价实现？**

- **部分等价。** Engine 1 的 `Library` 匹配就是"query 谱 vs 库谱"的打分，输出 `lib_max`、`lib_mean`、`lib_shift`、`lib_cnt`（Engine 2 的 `molecule_channels` 里同名特征，`casmi_engine.py` L340-380），并且 `lib_max≥0.9` 会直接阻断 PubChem 门控。这已经是"1-NN per structure"的变体。【已核实（特征名与门控）/ 推断（具体相似度定义在 `casmi/library.py`，本地不可读）】
- **不等价的部分**：
  1. 没有"多邻居投票"（现在是每个结构一个合并分，不是 top-k 邻居加权）；
  2. 没有"跨结构"投票（邻居结构可以不是候选，但目前库里的结构都在池内，所以这一条增量小）；
  3. **没有把 `max_cos` 当作"答案是否在池内"的显式判据**——这是最新、也最可能有用的一点；
  4. 没有 modified cosine / 中性丢失匹配（Engine 1 用的是引擎自己的打分）。

**增量**

- 排序：预计小（与库匹配共线）。066a 的"连续余弦 mid-rank"在 0.488 上中性，N-1c 的"测试集内网络"只 +0.001，两个最近的同类实验都说明**库/网络信号的排序增量在 3 位小数内**。
- **门控：增量可能更大。** 用 `max_cos` 区分"池内有答案"与"池外"，可以让 L1 的 PubChem 升位只在真正需要时开火，从而降低 L1 的风险。

**如何离线测 recall@25（可直接执行）**

1. 从 `train.parquet` 取 `inchikey14`，按结构整组留出 **2,000** 个（约 0.7%），确保 query 的谱全部从索引中删除。
2. 用剩余 2.5M 谱建索引（0.01 Da 分箱、sqrt 强度、最多 120 峰），对每个 query 取 top-20 邻居。
3. 计算：
   - `recall@25 = P(真值 ∈ top-25 投票结构)`；
   - `MRR@25`、`top1`；
   - 分层：`max_cos ∈ [0.9,1] / [0.7,0.9) / [0.5,0.7) / <0.5` 四档的 recall 与 top-1；
   - 与"现有 `lib_max` 排序"做配对比较（同一批 query，看 wins/losses）。
4. 判据：只有当 `recall@25` 相对现有库匹配**提升 ≥2 个点**，且 `max_cos<0.5` 档确实对应低 recall（说明门控有效），才值得进 068b。

**预算**：索引 30 分钟 + 2,000 次查询（秒级/百次），**CPU only**。

**结论**：**(b) 作为"直接投结构票"的提分手段，预期 +0.000～+0.01，低于 (a) 的正确形态；但作为 L1 的"升位门控"有独立价值，建议与 L1 一起做，而不是单独做。** 【推断】
